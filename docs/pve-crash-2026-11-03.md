# PVE cluster hard crash — 2026-11-03 19:01Z (13:01 CST)

Status: **confirmed crash, cause not yet read (root-gated)**. Written from non-root evidence only.

## What happened

`last reboot` on all three nodes shows **"- crash"** (no clean shutdown recorded), i.e. the
machines went down hard rather than rebooting cleanly:

| node | crash boots (CST) | recovery boot |
|---|---|---|
| pve01 | 13:02 | 13:44 |
| pve02 | 13:01, 13:07 | 14:56 |
| pve03 | 13:02, 13:24 | 14:58 |

All three first went down **within the same minute** (13:01-13:02 CST / **19:01-19:02Z**), which
points at a *common* cause rather than three independent faults. Further crashes at 13:07 (pve02)
and 13:24 (pve03) happened while the cluster was still coming back. Total disruption per node:
**42 min (pve01) to ~2 h (pve02/pve03)**.

At the time of writing (23:44 CST) all three are up: pve01 9 h 59 m, pve02 8 h 47 m, pve03 8 h 45 m.

Context: the ZFS ARC Oops fixed by kernel **7.0.14-26** (see `pve-node-freeze-2026-10.md`) is a
*different, earlier* incident; these nodes are already running 7.0.14-26. Whether this is a new
kernel fault or an external event (power, hardware, shared dependency) is exactly what the crash
record would say.

## Why the cause is not in this note

The evidence is root-only on the PVE nodes, and every non-root route has been checked:

- `amd` is in groups `amd, sudo` only — **not** `adm`/`systemd-journal`, so `journalctl -b -1`
  returns "No journal files were opened due to insufficient permissions".
- `/sys/fs/pstore/` → **Permission denied** (root-only).
- No `/var/log/syslog`, no `/var/log/kern.log` (journal-only systems).
- `ssh root@pve01` with the ansible key → **`Permission denied (publickey)`**, i.e. the auth model
  holds: no privileged access without the YubiKey.
- `sudo` on the nodes requires the local YubiKey (pam_yk), which is not inserted.

## To finish this

With the YubiKey inserted (or root access granted another way), on each node:

```
sudo journalctl -b -1 -k --no-pager | tail -200     # the crashing boot's kernel log
sudo ls -l /sys/fs/pstore/ && sudo cat /sys/fs/pstore/*   # panic record, if any
sudo journalctl -b -2 -k --no-pager | tail -50      # the boot before the second crash (pve02/03)
```

Look for: a kernel Oops/panic (new fault), a power-loss signature (all nodes at once, no panic),
or a fencing event (HA/quorum). Cross-check the switch port counters and UPS logs for the same
minute if no panic is present.
